# Gameplay experience

### EXP-GAME-001 — Resolve project terminology to canonical mechanics before research or implementation

- Status: active
- Scope: gameplay specification, balance research, localization, and research-to-production handoff; Timeline Real/Parallel effects; canonical Infinity/IP gain semantics
- Learned from: Issue #217; Issue #237; Issue #245; Issue #273; Issue #341; PR #236; PR #253; PR #283
- Context: Real-BC16500 used the Japanese term `Infinity獲得量`, while Parallel-BC16500 used `IP獲得量`. Existing Infinity Challenge 6 copy already established `Infinity獲得量` as `Infinity count gain`, but #217 normalized Real to `IP gain × (1 + log10(current IP))`. The research simulator and checkpoint study measured that historical interpretation, #245 promoted it to an approved production formula, and PR #253 implemented/tests it through the Infinity Point gain path. #273 later restored the original Japanese wording while preserving the implementation. Issue #341 rechecked the original term and canonical path, marked the Real IP interpretation superseded, and moved production Real to `infinityCountGain()` while keeping Parallel on IP gain.
- Cause: a project-specific gameplay term was translated and normalized before it was mapped to the existing canonical mechanic. The resulting research assumption was later treated as production authority without re-checking the original source wording and established bilingual terminology. A copy-only scope then preserved the behavior instead of surfacing the semantic conflict for follow-up.
- Reusable lesson: before converting gameplay prose into English, formulas, research hooks, or implementation targets, map each domain term to its canonical state/action/function using existing code and bilingual examples. Do not infer that nearby terms such as `Infinity獲得量` and `IP獲得量` mean the same mechanic. Research parameters are evidence, not production authority: when promoting research into a production Issue, re-check the original design wording and canonical mechanic. If player-facing/spec wording conflicts with current behavior, surface the mismatch even when changing behavior is outside the current Issue's scope.
- Verification: for a gameplay effect, search existing Japanese/English pairs and the canonical runtime functions before fixing the target mechanic; for Infinity-related effects, distinguish `infinityCountGain()` from `infinityPointGain()`. Before a research result becomes a production specification, compare its nouns, target resource, and formula back to the original design wording. During copy-only work, treat a source-wording/implementation mismatch as a blocker or follow-up candidate instead of silently making the wording conform to the implementation. For Real-BC16500, validate the IP multiplier helper is inactive and the count multiplier is applied once through `infinityCountGain()`.
- Authoritative at: Issue #341 production runtime and regression tests; the #217/#237 Real IP rows remain historical superseded evidence
- Last verified: 2026-09-05

### EXP-GAME-002 — Do not redefine relative gameplay scaling from existing implementation baselines

- Status: active
- Scope: gameplay formulas, balance changes, Timeline effects, existing-reward scaling, formula migration, and regression-test expectation design
- Learned from: Issue #369; Issue #386; PR #372; PR #389
- Context: Real-BC6000 was originally described as strengthening the existing IC6 reward once per Eternity. During #369 specification/implementation work, that relative strengthening was rewritten as a final absolute IC6 reward of `2^E`, with `E = 1` explicitly forced to equal the pre-existing IC6 `×2` reward. The B2 critique then treated applying another `×2` at `E = 1` as "double counting" because `infinityCountGain()` already contained IC6's base `×2`, and implemented the Timeline contribution as `effectiveLog - log10(2)`. Regression tests fixed `E = 1 -> ×2` and `E = 4 -> ×16` as expected behavior. #386 later changed the per-Eternity coefficient from `×2` to `×1.2` but preserved the same baseline-subtraction model, carrying the earlier interpretation forward.
- Cause: a relative modifier to an existing gameplay reward was normalized into an absolute final multiplier by reasoning backward from the current implementation baseline. The existing IC6 `×2` was treated as something that must be subtracted from the new scaling instead of first determining whether the design intended `existing reward × per-Eternity modifier`. Once that reinterpretation entered the Issue, planning and tests reinforced it as canonical behavior.
- Reusable lesson: when a specification says an existing reward/effect is "strengthened", "multiplied", or otherwise scaled, do not infer the final absolute value from the current implementation baseline. First classify the wording as either (a) a relative modifier applied to the existing effect or (b) a replacement/final absolute formula. Never introduce baseline cancellation such as `-1`, division by the old multiplier, or `-log10(base)` solely because the old effect is already present in code. A current implementation detail is not evidence that a newly specified multiplier would be "double counted". Re-derive the formula from the design wording before adapting existing code.
- Verification: before implementation, write at least two small source-derived examples for the changed formula, especially the first nonzero progression state such as `E = 1` and a later state such as `E = 2`. Compare those examples independently against the existing base effect and the proposed composed formula. Inspect any subtraction/division/baseline-offset in the implementation and require a source-level reason for it. Regression tests must encode expectations derived from the specification or explicit maintainer decision, not values reverse-engineered from the current code. Passing tests do not validate a formula when the expectations were generated from the same mistaken interpretation.
- Last verified: 2026-09-17
